# Pathwise 长期产品目标与执行路线

## 长期目标（North Star）

把 Pathwise 做成一个“以真实证据驱动路线变化”的职业成长操作系统：用户每次提交简历、项目成果或面试反馈，系统都能说明岗位判断哪里变了、哪个缺口被缩小或暴露、现在唯一最值得做什么，并在下一次行动完成后继续闭环。

长期验收同时满足四个条件：

1. **主线确定**：所有功能都服务于“事实 → 判断 → 行动 → 证据 → 重算”，不做孤立的 AI 玩具。
2. **实际有用**：核心指标是有成果证明的有效职业行动完成率，而不是生成字数、点击数或打分。
3. **可以商业化**：免费本地/自托管体验建立信任，个人 Pro、学校/训练营工作台、企业招聘与成长 API 分层变现。
4. **可以传播**：一键部署、隐私可信、匿名案例可复现、文档和演示完整，最终以 GitHub 10,000+ Stars 作为开源影响力验收线。

## 四条不可偏离的产品原则

- 今日规划永远只突出一个优先行动；其它建议降级为背景信息。
- 承诺不等于进度，只有执行事实和可复核成果才能推进路径。
- AI 负责解释和候选建议，确定性模型负责状态迁移、难度加权和路径分叉。
- 默认不上传个人材料；任何岗位结论都能回溯到证据来源、时间和置信度。

## 分阶段路线

### Phase 0：可信闭环（当前，0–3 个月）

目标：让陌生用户 clone 后 10 分钟内完成一次可复现闭环。

- P0 可靠性：统一本地服务与 Pages Functions 的错误码、超时、流式截断和旧规划回退。
- P0 体验：空状态 → 建立画像 → 唯一行动 → 提交成果 → 看到路线变化；移动端无横向溢出。
- P0 算法：稳定的 Plan/Evidence/Trajectory schema，所有迁移都有测试和版本号。
- 发布门槛：`npm test`、页面 smoke、无 Key deterministic demo、脱敏合成案例和 90 秒演示。

### Phase 1：证据原生（3–9 个月）

目标：让每个岗位判断都能被证据解释，让新材料真正改变路线而不是重新生成长文。

- 统一 Evidence schema：`source`、`capturedAt`、`confidence`、`supports`、`exposesGap`、`impact`。
- 岗位判断支持“证据句 → 匹配变化 → 首行动变化”的可追溯链。
- 地图、成长报告和行动指导共享同一份状态，不重复维护业务逻辑。
- 增加匿名本地评测集：规划有效性、证据影响准确率、行动可执行性、隐私泄露回归。

### Phase 2：工作台与商业化（9–18 个月）

目标：从个人工具升级为可信的成长工作台，同时保留开源核心。

- 个人 Pro：多目标路线、版本对比、提醒与导出、可选模型和加密同步。
- 学校/训练营：班级匿名进度、导师批注、证据模板和群体缺口分析，不暴露个人简历原文。
- 企业/API：岗位能力模型、候选人自评与成长建议 API；明确“辅助决策而非自动淘汰”的边界。
- 商业指标：激活率、有效行动完成率、7 日有效证据新增率、付费留存；不以模型调用量作为北极星。

### Phase 3：开源网络效应（18–36 个月）

目标：成为职业成长领域最容易部署、最可信、最有连续性的开源产品之一。

- 插件化 Evidence adapters（简历、GitHub、作品集、面试复盘、课程项目）。
- 可审计的评测与公开 changelog；每次算法变化都提供前后样例和迁移说明。
- 贡献者路径：good first issue、案例/数据贡献规范、主题包和本地化文档。
- 传播资产：真实匿名案例、可 fork demo、架构图、隐私白皮书和可嵌入分享卡片。
- 1 万 Star 的必要条件：产品可用性、安装成功率、文档质量、持续发布节奏与社区问题响应同时达标；不刷量、不用虚假案例。

## 研发与算法边界

```text
事实输入 → Evidence schema → 确定性状态迁移 → AI 解释/候选 → 唯一行动
    ↑                                                   ↓
    └────────────── 成果与外部反馈 ← 行动完成 ────────────┘
```

- 前端只消费同源 `/api/*`，Key 只在本地环境或 Cloudflare Secret。
- AI 输出必须过 schema、占位符拦截、长度限制和旧规划保护；失败时回退规则引擎。
- 进度按行动难度、投入和成果质量加权，不能按勾选数量增长。
- 所有新功能评审时回答：它输入了什么事实？改变了什么判断？产生了什么行动或反馈？

## 每轮开发的决策顺序

1. 先修复数据丢失、错误误导、隐私和移动端可用性问题。
2. 再强化“证据导致路线变化”的可解释性。
3. 最后才增加地图、动效和传播包装，并要求能提升有效行动完成率。

任何不满足主线、没有测试或无法说明用户收益的功能，进入 backlog，不进入主界面。
